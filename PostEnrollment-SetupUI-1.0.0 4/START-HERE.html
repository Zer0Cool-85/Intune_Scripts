Hotfix 8: Read run logs in File Explorer

Earlier live runs granted full control to SYSTEM and the local Administrators group. Ordinary File Explorer uses the user's non-elevated token, so even a local administrator may be unable to browse that directory without elevation. The files were not intentionally limited to SYSTEM alone.

New runs

The default now grants the Explorer owner in the setup session read/execute access to that run folder and its contents, while SYSTEM and Administrators keep full control. The reader cannot modify/delete the logs or worker control files. State and Runs parent folders grant folder-only navigation/listing access; that reader permission does not inherit into Completed-*.json or other runs.

This works with the existing SYSTEM + ServiceUI launch. The resolved reader SID is recorded in SetupUI.log. If the user cannot be identified, setup continues with the explicit readers (if any) plus SYSTEM/Administrators, and records the reason in the log. A SYSTEM process in session 0 needs explicit LogReaderSids. The configured StateDirectory parent is not re-permissioned. If you deliberately restricted that custom parent, its navigation permissions also need consideration.

Run-folder access covers transcripts, MSI/servicing logs and diagnostic JSON, including request parameters. Do not put credentials into step parameters or logs. This permission grants access; it does not redact existing file contents.

Optional settings inside Behavior (old JSON receives these defaults in memory):

"AllowInteractiveUserToReadLogs": true,
"LogReaderSids": []

Set AllowInteractiveUserToReadLogs to false and leave LogReaderSids empty to keep new runs restricted to SYSTEM/Administrators. Alternatively add exact Windows user/group SID strings to LogReaderSids for additional readers. Group access depends on that group's SID being present in the reader's Windows token. These settings do not make anyone an administrator or grant write access.

Changing settings governs new run folders and current parent navigation grants; it does not revoke read grants already attached to previous run folders. Keep an additional support reader in LogReaderSids if that account must continue browsing the parent folders after later launches by other users.

Changed detection

Another user's installation and a Staged entry do not count as success. AppX query errors still fail the step; they do not become a missing-app result. Hotfix 6: IsSelected startup error

The enterprise JSON is valid without an IsSelected field. IsSelected is a property on the UI's compiled C# StepViewModel, not a configuration setting. Every step, including automatic steps, initializes that property.

The earlier startup code reused any DeviceSetupUI.StepViewModel already loaded in the current PowerShell process. If an older release had been run in the same ISE/PowerShell host, that cached class could lack the optional-selection properties. An older UI/StepViewModel.cs file mixed with newer PowerShell files could produce the same missing-property symptom. Without the original error's script location, these are supported causes, not proof of which occurred on a particular device.

Hotfix 6 loads the model under a namespace derived from its source hash, so a different source revision cannot reuse the earlier class. It also validates the selection properties before constructing the window. Old model files now produce a specific version-mismatch message identifying the files to update.

Common behavior and logs

  • Human-readable progress, outcomes and errors go to the current run's SetupUI.log, alongside the UI's entries. Worker transcripts remain separate.
  • Existing successful steps are resumed by the framework. Re-running a script also checks current detection state before installing.
  • Exceptions fail the step and appear in the UI; native MSI 3010 reports a restart requirement. No supplied script initiates a reboot.
  • Use SuccessExitCodes: [0, 3010] and RebootExitCodes: [3010] as in the example.
  • Set the UI timeout comfortably above the installer duration, busy retries, Store registration and Intune wait. A UI timeout is not a safe installer cancellation mechanism. Inspect device state before retrying a timed-out install.
  • Imported helper files and payload bytes are not part of the existing step fingerprint. Use a new, deliberate SetupVersion for a changed deployment release when you need completed steps reconsidered. Re-running cleanup after production apps are installed can remove matching apps again; review its scope.
  • Detection is point-in-time. This first-logon UI does not replace ongoing Intune application detection, compliance, or update management.

The interactive helper uses a temporary Task Scheduler task running as the identified user with limited privileges and no stored password. SYSTEM independently checks the resulting app/registry state. It does not trust a user-writable success marker. The task is stopped/unregistered in normal cleanup; after a forced power-off, remove stale PostEnrollment-UserAction-* tasks during your pilot cleanup. They have no trigger and a bounded execution time.

1. MSI installer

Script: EnterpriseSteps/Step-InstallMsi.ps1

"Parameters": {
  "MsiRelativePath": "Payloads/MSI/YourApp.msi",
  "ProductCode": "{REPLACE-WITH-THE-REAL-MSI-PRODUCT-GUID}",
  "MinimumVersion": "1.2.3",
  "Properties": ["DESKTOPSHORTCUT=0", "COMPANYNAME=\"Example Company\""],
  "ExpectedSha256": "",
  "RequireValidSignature": true,
  "AppendVerboseLogToPrimary": true,
  "BusyRetries": 3,
  "BusyRetrySeconds": 30
}

Use the MSI ProductCode, not UpgradeCode or PackageCode. Obtain it from the vendor/MSI metadata or an approved test installation's uninstall key. A changed ProductCode on a major upgrade needs updated detection configuration. Detection uses the two machine uninstall registry views and optional minimum DisplayVersion; it never queries Win32_Product. Version strings must be .NET-style numeric versions (for example 1.2.3, not 1.2.3-beta). Per-user MSI installs and products that intentionally omit those machine uninstall keys need custom detection.

The script runs /qn /norestart, forces ALLUSERS=1 and REBOOT=ReallySuppress, and accepts MSI properties as an array. It rejects scope/reboot overrides and does not support raw installer switches, transforms or EXE installers. Test your vendor's silent installation contract first. A valid Authenticode signature is required by default; ExpectedSha256 optionally pins the exact approved file. For a legitimately unsigned internal MSI, explicitly set RequireValidSignature false and pin its approved hash.

It retries 1618 (another installation in progress), accepts 0/3010, and verifies ProductCode/version afterward. Other codes fail. A success exit code with failed detection is a failure, not a green checkmark.

The native *-MSI-*.log is kept separately. By default, its contents are appended to SetupUI.log after msiexec exits, tagged [MSI]. This avoids two programs writing different formats to the same file. Live UI messages are milestones, not an invented MSI percentage. Set AppendVerboseLogToPrimary false for summary entries and a path to the verbose log. Installer logs can expose property values; do not pass secrets in Properties and protect/retain logs according to policy.

2. Company Portal detection and registry flag

Script: EnterpriseSteps/Step-DetectCompanyPortal.ps1

"Parameters": {
  "RegistryPath": "HKLM:\\SOFTWARE\\YourCompany\\PostEnrollmentSetup"
}

In the native 64-bit registry view, this writes:

Value Type Meaning
NeedsCompanyPortal DWORD 1 = missing/unhealthy for the setup user; 0 = present and healthy
TargetUserSid String User whose app registration was checked
CheckedUtc String UTC time of the latest check
DetectionScope String InteractiveUserRegistration

The script resolves the owner of Explorer in the setup process's session. You may explicitly supply TargetUserSid for an already interactive Explorer user; it will not select an arbitrary other user if identification fails. It queries Microsoft.CompanyPortal using AllUsers, then requires that user's exact SID with InstallState=Installed, Microsoft publisher, Status=Ok and no partial staging. Merely being provisioned or installed for another user does not count as ready. A missing app is logged and flagged without failing the step, so its dependent installer can run. This tells you whether Portal is available at this check. It cannot prove whether enrollment installed it earlier or whether someone removed it afterward. The flag is a current-state marker, not immutable enrollment history.

Writing your setup steps

The execution contract

Each enabled step is executed sequentially in a fresh, hidden 64-bit Windows PowerShell 5.1 process. When the parent is launched as SYSTEM through your ServiceUI workflow, its workers also run as SYSTEM. A step does not share local variables or functions with another step.

The framework starts a transcript, supplies progress/installer helper functions, runs your script, and checks the process exit code. The UI remains on its own thread/process while the worker does the slow work.

  1. Keep $ErrorActionPreference = 'Stop' in your script.
  2. Detect the existing state before making changes. Steps must be safe to run again after interruption or failure.
  3. Apply the change.
  4. Verify the resulting state.
  5. Return normally for success; throw a useful message for failure.

Returning $false, outputting the word Failed, or using Write-Warning does not mark a step failed.

Minimal example

Replace a placeholder step with your own code using this pattern:

[CmdletBinding()]
param()
$ErrorActionPreference = 'Stop'

Write-SetupProgress -Message 'Applying configuration...' -Percent 10

# Your real PowerShell commands go here.

Write-SetupProgress -Message 'Verifying the result...' -Percent 90

# Example: if your actual detection fails, throw a meaningful error.
# if (-not (Test-YourResult)) { throw 'The expected setting was not applied.' }

Write-SetupProgress -Message 'Configuration verified.' -Percent 100

This is a writing pattern, not a ready-made configuration action. The included Steps/Step-XX.ps1 files retain a deliberate throw until you implement them, so an untouched placeholder cannot report success in production.

Sending progress

Write-SetupProgress -Message 'Downloading application files...'
Write-SetupProgress -Message 'Installing the application...' -Percent 45
Write-SetupProgress -Message 'Validating installation...' -Percent 95

Message updates the current card's detail line. Omitting Percent hides the per-step percentage bar while the spinner continues. Percentages are estimates you supply; the framework does not read an installer's internal progress. The overall bar weights each configured step equally and measures finished work, including failures/skips. Overall text and colors show whether the result succeeded.

Running installers and preserving exit codes

Prefer the supplied helper:

$installer = Join-Path $env:SETUP_PACKAGE_ROOT 'Files/AppSetup.exe'
$null = Invoke-SetupProcess -FilePath $installer -Arguments '/quiet /norestart'

Invoke-SetupProcess waits for the process tree, accepts 0 and 3010 by default, throws on other codes, and remembers a reboot-required result. Use the vendor's actual silent/no-restart arguments; EXE switches are not standardized.

Override acceptable codes when required:

$null = Invoke-SetupProcess -FilePath $installer -Arguments '/S' -SuccessExitCodes @(0,3010) -RebootExitCodes @(3010)

For raw native commands, check the exit code immediately:

& $installer /quiet /norestart
$installExit = $LASTEXITCODE
if ($installExit -notin @(0,3010)) { throw "Installer failed: $installExit" }
if ($installExit -eq 3010) { exit 3010 }

A final nonzero $LASTEXITCODE is preserved by the worker when the step returns. An explicit exit N is also honored. Earlier native failures can be overwritten by later native commands, so check each command or use the helper. If you intentionally handle a nonzero code and recover, return an explicit exit 0 or reset $global:LASTEXITCODE = 0 after verification. The JSON step's SuccessExitCodes controls final acceptance; RebootExitCodes must be a subset of it.

The framework displays a restart reminder and returns 3010 when needed. It does not reboot. Suppress automatic reboots in each installer so they cannot interrupt the checklist unexpectedly.

Dependencies, failures, and retry

  • A step may depend only on earlier enabled step IDs.
  • A failed/skipped dependency causes the dependent step to be skipped.
  • With StopOnRequiredFailure: false, independent later steps can continue.
  • With StopOnRequiredFailure: true, a required failure skips all remaining steps.
  • Optional failures remain visibly failed but do not make the overall deployment fail if all required steps succeeded.
  • Retry unfinished resets only failed/skipped included steps. Unselected options are excluded. Successful steps remain completed. Dependencies are checked again.
  • There is no unlimited automatic retry loop.
  • A timeout always stops the run and disables in-window retry. The framework asks Windows to terminate the worker process tree; a service-owned MSI/custom installer operation may outlive that tree. Inspect device/installer state before restarting the workflow.

Completion and resume

With ResumeCompletedSteps: true, a successful step is remembered. Its fingerprint includes its script content, configured parameters, success/reboot codes, and dependency fingerprints. Changing a step or one of its declared dependencies causes affected work to run again. Changing only branding or wording does not.

External installer contents and helper files imported by your script are not automatically fingerprinted. Bump SetupVersion when those inputs change and you want steps reconsidered. Detection inside each step remains essential. A saved success is a record of previous execution, not continuous compliance monitoring.

ServiceUI.exe -process:explorer.exe C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo -NoProfile -STA -WindowStyle Hidden -ExecutionPolicy Bypass -File "C:\Program Files\YourCompany\DeviceSetup\Start-DeviceSetup.ps1" -ConfigPath "C:\Program Files\YourCompany\DeviceSetup\Config\Setup.json" -Live

Use your actual Windows/install paths. Run-Live-ServiceUI.cmd uses variable-based Windows paths and expects x64 ServiceUI.exe, which resolves System32 to 64-bit PowerShell. Do not pass a Sysnative path to an x64 ServiceUI process. To use it, place your existing x64 ServiceUI.exe in Tools, then invoke the CMD from your SYSTEM deployment mechanism. Double-clicking it as a normal user does not grant SYSTEM privileges; the live-mode identity check will reject that run by default.

The sample targets explorer.exe. Keep your existing session-selection logic if you support RDP, fast user switching, or multiple signed-in sessions. A process-name match is not a robust way to identify the intended employee on a multi-session computer.

Installation location and permissions

Use a local protected folder such as C:\Program Files\YourCompany\DeviceSetup. Preserve SYSTEM/Administrators write access and ordinary-user read/execute access. Scripts, XAML, executable files, and JSON control SYSTEM execution and must not be writable by standard users. Do not run the live package from an employee-writable Downloads/Desktop folder.

Use your organization's approved script-signing/application-control approach. The sample commands use ExecutionPolicy Bypass for packaging convenience; this does not bypass WDAC/AppLocker or other enforcement policies.

The UI intentionally has no Open File, Open Log, or browser-launch buttons; diagnostics are displayed as text and can be copied. Users can minimize the window while work runs. Close/Alt+F4 is ignored until the run finishes; this is a workflow behavior, not a kiosk/security boundary.

Intune integration

  1. Package your completed folder with your normal Win32 packaging process.
  2. Use your existing SYSTEM staging/install script to copy it to a protected local folder.
  3. Detect that the framework is staged, using your existing version/file marker.
  4. Let your existing first-desktop/after-ESP trigger launch the ServiceUI command.
  5. Retain your completion/cleanup flow or use this package's completion records to avoid repeating successful work.

Do not make an ESP-blocking staging app wait for these desktop-only steps. ESP must be able to finish before the first-desktop launcher can run. The framework's staging detection and the final-setup completion result are separate concerns.

ServiceUI cannot show the popup before the target desktop/session exists. Keep your current enrollment-completion checks; a fixed sleep is not sufficient to identify the end of every provisioning scenario.

State and log locations

Default live location:

C:\ProgramData\Company\PostEnrollmentSetupUI\Company.DeviceSetup\

StateDirectory is the configured parent; SetupId is appended automatically. In SYSTEM live mode, SYSTEM and Administrators retain full control. By default, the interactive user gets read-only access to the new run folder, plus folder-only navigation permissions on the package and Runs folders. Completion-state files do not inherit that reader grant. The configured parent itself is not re-permissioned. See log access and existing-run repair.

File/folder Purpose
Completed-1.0.0.json Success records and declined options for that SetupVersion
Runs//SetupUI.log Controller status transitions
Runs//stepXX-attempt-N.log Per-attempt PowerShell transcript
Runs//*.request.json Parameters and paths given to the step worker

Demo runs use %LOCALAPPDATA%\PostEnrollmentSetupUI\Demo\Runs. They never update live completion state.

Completed work is skipped on later launches. With ResumeCompletedSteps=true, explicit declines are also remembered. If every enabled step is complete or declined with matching fingerprints, live mode exits without displaying a window. Incomplete/failed automatic work is reconsidered; incomplete/failed user-selectable work is offered unchecked again. This is once-per-device behavior, not once per employee profile.

Logs are not automatically deleted. Apply your normal endpoint log-retention policy. Never write credentials to messages, parameters, or transcripts.

Offering optional apps again

Add -ChooseOptional to the existing SYSTEM + ServiceUI command to reoffer unfinished optional apps. Completed work stays completed. User choices are made before any step runs; automatic steps wait until Start setup is selected when choices are available. Old configurations without UserSelectable keep automatic execution. See hotfix 4 for details.

The script sets a process-wide AppUserModelID before presenting the WPF window. Run it in its own powershell.exe process. Keep -WindowStyle Hidden to avoid showing a separate console window. The window icon can be customized with Branding.IconPath; the underlying executable remains powershell.exe.

Resetting for a controlled retest

Use -ResetState -Live with the same SYSTEM launcher to archive the completion file and reconsider all enabled steps. This can repeat installations/configuration, so use it only when you intend a full retest. It does not uninstall anything. The normal in-window retry leaves successful steps untouched.

For a new intended setup revision, change SetupVersion. Changing only SetupId also creates a separate state namespace, so keep IDs stable unless you intend a new workflow.

Return codes

Exit code Meaning
0 All required steps succeeded; optional failures may still be present in Results.json
1 A required step failed/skipped, or setup encountered a configuration/controller error
3010 Required work succeeded and a successful step requested reboot; no reboot is initiated
1618 Another instance of this package is already running
2 from CMD wrapper ServiceUI.exe is missing

The default window remains open at the result screen until Done is selected; the parent launch does not finish until then. To close automatically after full success, set AutoCloseSuccessSeconds, for example 10. Warnings/failures remain visible. A reboot request is retained across launches until the detected Windows boot time changes.

Updating the package

Keep your production scripts/config and review changes before replacing the framework. Retest using the actual ServiceUI command, standard-user desktop, screen scaling, app-control policies, and your intended post-ESP timing. Do not upgrade a package while one of its live steps is running.

What has and has not been tested

The authoring environment is Linux. Validation here covers PowerShell source syntax with a tree-sitter parser, JSON/schema consistency, package paths/dependencies, XAML XML/resource/name references, documentation links, and the HTML design reference.
