Post-enrollment Setup UI

Version 1.0.0 · Windows PowerShell 5.1 · WPF · Your existing SYSTEM + ServiceUI launch

A configurable, Fluent-inspired first-desktop setup window. Keep your current post-enrollment trigger and replace the popup with this front end. Add your PowerShell code to individual step files; the window handles progress, animation, status, and results.

Start here

  1. Extract the entire ZIP to a local folder on a Windows test PC.
  2. Double-click Run-Demo.cmd. No administrator rights are needed for the demo.
  3. Watch the third step fail intentionally and the dependent fourth step become skipped. Expand its technical details, then choose Retry unfinished. The retry succeeds.
  4. Edit Config/Setup.json to change your company name, welcome text, theme, logo/banner paths, and step labels.
  5. Put your actual commands in Steps/Step-01.ps1 through Step-10.ps1. Remove the placeholder throw in each step you implement.
  6. Disable unused entries with "Enabled": false. Reorder the JSON objects to change execution order.
  7. Run Validate-Config.cmd, then the Windows smoke tests in Tests/Invoke-SmokeTests.ps1.
  8. Pilot live execution using your existing SYSTEM + ServiceUI workflow with -Live. See deployment instructions.

Safe by default: launching Start-DeviceSetup.ps1 with no mode switch runs a simulation. Only -Live executes your step scripts. All ten supplied step scripts deliberately fail in live mode until you replace their placeholders. Demo mode never calls those scripts.

Quick commands

From an extracted package folder in Windows PowerShell:

# Safe simulation; no step scripts run.
powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\Start-DeviceSetup.ps1 -Demo

# Dark theme example.
powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\Start-DeviceSetup.ps1 -Demo -ConfigPath .\Config\Dark-Demo.json

# All 10 steps enabled, to inspect the scrolling layout.
powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\Start-DeviceSetup.ps1 -Demo -ConfigPath .\Config\All10-Demo.json

# Configuration-only check; no UI or steps.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-DeviceSetup.ps1 -ValidateOnly

# Windows tests; no app installs or ServiceUI invocation.
powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\Tests\Invoke-SmokeTests.ps1

The demo/config-check CMD launchers choose Sysnative when called from a 32-bit process. The live wrapper instead expects x64 ServiceUI, which launches 64-bit PowerShell through System32.

Scope and compatibility

  • Target: Windows 10/11 x64 with Windows PowerShell 5.1 and the Windows WPF/.NET Framework components.
  • The UI requires an STA session. PowerShell 7 is intentionally rejected for the UI to keep one supported host/runtime target.
  • Your ServiceUI launcher, first-logon scheduling, and enrollment/ESP readiness checks remain your responsibility.
  • This is device-level completion tracking. HKCU, APPDATA, and USERPROFILE refer to SYSTEM in a SYSTEM-run step, not the signed-in user.
  • ServiceUI.exe and application installers are not included.
  • No network calls, telemetry, package downloads, or built-in application changes are performed by the framework. Your live step scripts determine those actions.

Verification status

Source parsing, configuration checks, XAML/XML structure, resource/element references, package links, and the HTML design reference are checked in the build environment. That environment is Linux, so Windows PowerShell execution, WPF rendering, ServiceUI session presentation, and real installers have not been run here. The included Windows smoke tests and pilot checklist cover those remaining checks.

Configuration reference

Edit Config/Setup.json with a text editor. JSON requires double quotes, lowercase true/false, and no comments or trailing commas. Forward slashes in paths work on Windows and avoid JSON backslash escaping. Run Validate-Config.cmd after editing.

Step order and dependencies

Steps run in their JSON array order, not numeric ID order. Reordering does not require renaming files. A dependency must point to an earlier enabled step. A disabled dependency is a validation error, so remove/change that reference when disabling a prerequisite.

Advanced visual changes

Edit UI/MainWindow.xaml for corner radii, card spacing, text sizes, the fixed DEVICE SETUP label, status badge layout, error-expander caption, or other strings outside the config. Edit the named resource brushes for light-theme backgrounds. Dark-theme background brushes are assigned in Start-DeviceSetup.ps1. Keep named controls, resource keys, and binding names intact unless you also update their code references.

The window uses a native Windows frame plus WPF content. Native title-bar appearance follows Windows; selecting the Dark preset changes the content and does not force a dark native frame. The window can be minimized, cannot be maximized, and clamps itself to the desktop work area. Very long text, large banners, or unusually high display scaling may require shorter text or a larger screen.

Writing your setup steps

The execution contract

Each enabled step is executed sequentially in a fresh, hidden 64-bit Windows PowerShell 5.1 process. When the parent is launched as SYSTEM through your ServiceUI workflow, its workers also run as SYSTEM. A step does not share local variables or functions with another step.

The framework starts a transcript, supplies progress/installer helper functions, runs your script, and checks the process exit code. The UI remains on its own thread/process while the worker does the slow work.

  1. Keep $ErrorActionPreference = 'Stop' in your script.
  2. Detect the existing state before making changes. Steps must be safe to run again after interruption or failure.
  3. Apply the change.
  4. Verify the resulting state.
  5. Return normally for success; throw a useful message for failure.

Returning $false, outputting the word Failed, or using Write-Warning does not mark a step failed.

Minimal example

Replace a placeholder step with your own code using this pattern:

[CmdletBinding()]
param()
$ErrorActionPreference = 'Stop'

Write-SetupProgress -Message 'Applying configuration...' -Percent 10

# Your real PowerShell commands go here.

Write-SetupProgress -Message 'Verifying the result...' -Percent 90

# Example: if your actual detection fails, throw a meaningful error.
# if (-not (Test-YourResult)) { throw 'The expected setting was not applied.' }

Write-SetupProgress -Message 'Configuration verified.' -Percent 100

This is a writing pattern, not a ready-made configuration action. The included Steps/Step-XX.ps1 files retain a deliberate throw until you implement them, so an untouched placeholder cannot report success in production.

Sending progress

Write-SetupProgress -Message 'Downloading application files...'
Write-SetupProgress -Message 'Installing the application...' -Percent 45
Write-SetupProgress -Message 'Validating installation...' -Percent 95

Message updates the current card's detail line. Omitting Percent hides the per-step percentage bar while the spinner continues. Percentages are estimates you supply; the framework does not read an installer's internal progress. The overall bar weights each configured step equally and measures finished work, including failures/skips. Overall text and colors show whether the result succeeded.

Running installers and preserving exit codes

Prefer the supplied helper:

$installer = Join-Path $env:SETUP_PACKAGE_ROOT 'Files/AppSetup.exe'
$null = Invoke-SetupProcess -FilePath $installer -Arguments '/quiet /norestart'

Invoke-SetupProcess waits for the process tree, accepts 0 and 3010 by default, throws on other codes, and remembers a reboot-required result. Use the vendor's actual silent/no-restart arguments; EXE switches are not standardized.

Override acceptable codes when required:

$null = Invoke-SetupProcess -FilePath $installer -Arguments '/S' -SuccessExitCodes @(0,3010) -RebootExitCodes @(3010)

For raw native commands, check the exit code immediately:

& $installer /quiet /norestart
$installExit = $LASTEXITCODE
if ($installExit -notin @(0,3010)) { throw "Installer failed: $installExit" }
if ($installExit -eq 3010) { exit 3010 }

A final nonzero $LASTEXITCODE is preserved by the worker when the step returns. An explicit exit N is also honored. Earlier native failures can be overwritten by later native commands, so check each command or use the helper. If you intentionally handle a nonzero code and recover, return an explicit exit 0 or reset $global:LASTEXITCODE = 0 after verification. The JSON step's SuccessExitCodes controls final acceptance; RebootExitCodes must be a subset of it.

The framework displays a restart reminder and returns 3010 when needed. It does not reboot. Suppress automatic reboots in each installer so they cannot interrupt the checklist unexpectedly.

Parameters

In your step script:

[CmdletBinding()]
param(
    [Parameter(Mandatory)][string]$MsiRelativePath,
    [Parameter(Mandatory)][string]$ExpectedFile
)

In that step's JSON entry:

"Script": "Examples/Step-InstallMsi.ps1",
"Parameters": {
  "MsiRelativePath": "Files/YourApplication.msi",
  "ExpectedFile": "C:/Program Files/Vendor/App/App.exe"
}

Parameters are passed as named PowerShell parameters, not evaluated as commands. Boolean JSON values can bind to boolean/switch parameters. Do not place passwords, tokens, or private keys in configuration or progress messages; request files and transcripts retain setup information.

Dependencies, failures, and retry

  • A step may depend only on earlier enabled step IDs.
  • A failed/skipped dependency causes the dependent step to be skipped.
  • With StopOnRequiredFailure: false, independent later steps can continue.
  • With StopOnRequiredFailure: true, a required failure skips all remaining steps.
  • Optional failures remain visibly failed but do not make the overall deployment fail if all required steps succeeded.
  • Retry unfinished resets only failed/skipped steps. Successful steps remain completed. Dependencies are checked again.
  • There is no unlimited automatic retry loop.
  • A timeout always stops the run and disables in-window retry. The framework asks Windows to terminate the worker process tree; a service-owned MSI/custom installer operation may outlive that tree. Inspect device/installer state before restarting the workflow.

Completion and resume

With ResumeCompletedSteps: true, a successful step is remembered. Its fingerprint includes its script content, configured parameters, success/reboot codes, and dependency fingerprints. Changing a step or one of its declared dependencies causes affected work to run again. Changing only branding or wording does not.

External installer contents and helper files imported by your script are not automatically fingerprinted. Bump SetupVersion when those inputs change and you want steps reconsidered. Detection inside each step remains essential. A saved success is a record of previous execution, not continuous compliance monitoring.

User-specific settings

These steps inherit SYSTEM. Reading or writing HKCU or APPDATA accesses the SYSTEM profile. Use your existing intentional user-context mechanism for settings that require the signed-in user; do not assume the visible window changes the worker's identity. This package does not introduce a separate user-context execution engine.

Examples supplied

  • Examples/Step-InstallMsi.ps1: local MSI, no-restart install, log, and simple file verification. Replace file-presence detection with version/product detection as appropriate.
  • Examples/Step-SetMachineSetting.ps1: example machine-registry setting and verification.

Neither example runs unless you explicitly reference it from the JSON configuration and launch -Live.

Deployment and your first-logon workflow

Keep the current launch approach

This package intentionally retains your SYSTEM + ServiceUI setup. It does not register scheduled tasks, change enrollment policies, replace ESP, or alter your current first-logon trigger.

Stage the complete folder locally before your existing post-enrollment launch runs. The main window launches hidden child processes for the individual steps and polls their status. The window and workers inherit the original SYSTEM identity.

Direct ServiceUI command

From your existing SYSTEM process, after the intended user's desktop exists:

ServiceUI.exe -process:explorer.exe C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo -NoProfile -STA -WindowStyle Hidden -ExecutionPolicy Bypass -File "C:\Program Files\YourCompany\DeviceSetup\Start-DeviceSetup.ps1" -ConfigPath "C:\Program Files\YourCompany\DeviceSetup\Config\Setup.json" -Live

Use your actual Windows/install paths. Run-Live-ServiceUI.cmd uses variable-based Windows paths and expects x64 ServiceUI.exe, which resolves System32 to 64-bit PowerShell. Do not pass a Sysnative path to an x64 ServiceUI process. To use it, place your existing x64 ServiceUI.exe in Tools, then invoke the CMD from your SYSTEM deployment mechanism. Double-clicking it as a normal user does not grant SYSTEM privileges; the live-mode identity check will reject that run by default.

The sample targets explorer.exe. Keep your existing session-selection logic if you support RDP, fast user switching, or multiple signed-in sessions. A process-name match is not a robust way to identify the intended employee on a multi-session computer.

Installation location and permissions

Use a local protected folder such as C:\Program Files\YourCompany\DeviceSetup. Preserve SYSTEM/Administrators write access and ordinary-user read/execute access. Scripts, XAML, executable files, and JSON control SYSTEM execution and must not be writable by standard users. Do not run the live package from an employee-writable Downloads/Desktop folder.

Use your organization's approved script-signing/application-control approach. The sample commands use ExecutionPolicy Bypass for packaging convenience; this does not bypass WDAC/AppLocker or other enforcement policies.

The UI intentionally has no Open File, Open Log, or browser-launch buttons; diagnostics are displayed as text and can be copied. Users can minimize the window while work runs. Close/Alt+F4 is ignored until the run finishes; this is a workflow behavior, not a kiosk/security boundary.

Intune integration

  1. Package your completed folder with your normal Win32 packaging process.
  2. Use your existing SYSTEM staging/install script to copy it to a protected local folder.
  3. Detect that the framework is staged, using your existing version/file marker.
  4. Let your existing first-desktop/after-ESP trigger launch the ServiceUI command.
  5. Retain your completion/cleanup flow or use this package's completion records to avoid repeating successful work.

Do not make an ESP-blocking staging app wait for these desktop-only steps. ESP must be able to finish before the first-desktop launcher can run. The framework's staging detection and the final-setup completion result are separate concerns.

ServiceUI cannot show the popup before the target desktop/session exists. Keep your current enrollment-completion checks; a fixed sleep is not sufficient to identify the end of every provisioning scenario.

State and log locations

Default live location:

C:\ProgramData\Company\PostEnrollmentSetupUI\Company.DeviceSetup\

StateDirectory is the configured parent; SetupId is appended automatically. In SYSTEM live mode, the package subfolder is ACL-protected for SYSTEM and Administrators. The configured parent itself is not re-permissioned.

File/folder Purpose
Completed-1.0.0.json Success records for that SetupVersion
Runs//SetupUI.log Controller status transitions
Runs//stepXX-attempt-N.log Per-attempt PowerShell transcript
Runs//*.request.json Parameters and paths given to the step worker
Runs//*.progress.json Latest live detail/percentage
Runs//*.result.json Worker completion/error details
Runs//Results.json Overall outcome and per-step results

Demo runs use %LOCALAPPDATA%\PostEnrollmentSetupUI\Demo\Runs. They never update live completion state.

Completed work is skipped on later launches. If every enabled step is already complete with matching fingerprints, live mode exits without displaying a window. Incomplete/failed work is reconsidered on the next invocation. This is once-per-device behavior, not once per employee profile.

Logs are not automatically deleted. Apply your normal endpoint log-retention policy. Never write credentials to messages, parameters, or transcripts.

Resetting for a controlled retest

Use -ResetState -Live with the same SYSTEM launcher to archive the completion file and reconsider all enabled steps. This can repeat installations/configuration, so use it only when you intend a full retest. It does not uninstall anything. The normal in-window retry leaves successful steps untouched.

For a new intended setup revision, change SetupVersion. Changing only SetupId also creates a separate state namespace, so keep IDs stable unless you intend a new workflow.

Return codes

Exit code Meaning
0 All required steps succeeded; optional failures may still be present in Results.json
1 A required step failed/skipped, or setup encountered a configuration/controller error
3010 Required work succeeded and a successful step requested reboot; no reboot is initiated
1618 Another instance of this package is already running
2 from CMD wrapper ServiceUI.exe is missing

The default window remains open at the result screen until Done is selected; the parent launch does not finish until then. To close automatically after full success, set AutoCloseSuccessSeconds, for example 10. Warnings/failures remain visible. A reboot request is retained across launches until the detected Windows boot time changes.

Updating the package

Keep your production scripts/config and review changes before replacing the framework. Retest using the actual ServiceUI command, standard-user desktop, screen scaling, app-control policies, and your intended post-ESP timing. Do not upgrade a package while one of its live steps is running.

Testing and troubleshooting

What has and has not been tested

The authoring environment is Linux. Validation here covers PowerShell source syntax with a tree-sitter parser, JSON/schema consistency, package paths/dependencies, XAML XML/resource/name references, documentation links, and the HTML design reference. These are useful static checks, not a substitute for the Windows WPF runtime.

Not executed here: Windows PowerShell 5.1, WPF XAML loading/rendering, the C# model under .NET Framework, ServiceUI session injection, SYSTEM execution, installer process termination, and actual application installs. No production-readiness or successful deployment claim is implied.

Windows smoke tests

From the extracted folder:

powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\Tests\Invoke-SmokeTests.ps1

The script parses the PowerShell files with Microsoft's actual PowerShell parser, loads all supplied configurations, exercises outcome/dependency logic, compiles the C# view model, loads/measures the WPF layout with ten step models, and runs temporary worker fixtures for success, failure, explicit 3010, helper-based 3010, and progress updates. It does not display the main window, install an app, touch HKLM, or call ServiceUI. Its temporary files are removed afterward.

Visual pilot

  1. Run Run-Demo.cmd as a regular user.
  2. Confirm the window fits the display and remains responsive throughout the demo.
  3. Confirm step 3 shows a failure and step 4 is skipped due to the dependency.
  4. Expand the error; verify the message is legible and selectable.
  5. Choose Retry unfinished. Only failed/skipped steps should run; all steps should then finish.
  6. Confirm Done closes the window. During active work, Close/Alt+F4 should leave the workflow running; minimize should work.
  7. Run the Dark-Demo and All10-Demo configurations shown in README.md.
  8. Test at your normal laptop resolution, 100/125/150/200% scaling, and your normal docked monitor setup. The step list should scroll, and the footer must remain reachable.
  9. Add your actual logo/banner and inspect cropping, long welcome text, and long step labels.

SYSTEM/ServiceUI pilot

  1. Work on a disposable/test device with your normal application-control policies.
  2. Put a harmless real action in one step, such as verifying an existing file. Disable the other steps. Keep RequireSystemForLive true.
  3. Stage the full package in a protected local folder and use your existing SYSTEM + ServiceUI first-desktop trigger.
  4. Confirm the expected logged-on session sees the UI and the step transcript reports the expected identity.
  5. Verify success, a deliberate throw, a declared dependency failure, and an optional failure.
  6. Run the package again. Matching successful steps should be skipped; if all work is complete, no window should appear.
  7. Change the test step's contents and rerun. Its fingerprint should change and the step should run again.
  8. Test a short time limit with a harmless sleeping step. The worker should be terminated, remaining steps skipped, and in-window retry hidden.
  9. Test reboot-required behavior using a harmless exit 3010 step. Confirm no reboot is initiated and the caller receives 3010 after Done.
  10. Test an interrupted run/logoff and a second simultaneous launch. Confirm retry/resume behavior and the 1618 duplicate-instance result.

Only then add the real application/configuration work and validate each action's detection and idempotence. Custom actions can impose limitations that the UI cannot infer.
